# The cursor path runs on a worker thread, the Preview on the main thread

The loop used to be serial: read the camera, prepare, track, run the Controller, draw, `imshow`, `waitKey`. The cursor moved once per trip, so the window's cost (about 19 ms in `imshow` and `waitKey` on the Mac, whatever the window size) was cursor latency too. We decided to split it into two threads. A worker thread runs the camera read, frame preparation, the Hand tracker, the Controller and the cursor output, and publishes an immutable Snapshot of the latest state into a single latest-value slot that each publish overwrites (no queue). The main thread owns the OpenCV window, because macOS needs window calls there, and draws whatever Snapshot is latest. Only the worker touches the Controller, the tracker, the camera and the cursor output, and the worker itself closes the tracker and releases the camera when its loop ends. The one exception is quitting while the worker is stuck (in a camera read, the tracker or the output) past the one-second stop timeout: the main thread then shuts the output, which lifts a held button once and ignores every later call, so a worker that wakes up and presses can never leave the button down. The main thread does not close the tracker or release the camera under a call that may still be running on them; they are released when the worker comes back, or by the process exit, which is harmless. `QuartzOutput` also guards its button state with a lock. The worker is a daemon thread, so a camera read stuck in native code cannot keep the process alive, but it is always stopped explicitly and waited for with a timeout. We considered drawing the window at 1x or smaller (rejected by the maintainer: it changes the Preview and did not move WIN) and a multiprocessing split (frames would cross a process boundary, and it is heavier than needed while MediaPipe and OpenCV release the GIL). The cost is threading code with its own tests, and the Preview can show fewer images per second than the cursor gets.
